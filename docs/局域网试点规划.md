## 1. 背景

当前项目是**单机单用户**版本：每台电脑各跑一份，学生本地使用，记录存在本机。这种方式不用运维，但教师收数据、统一环境、课堂管理都不方便。

本规划要做的是**局域网小班试点**：一台主机跑服务，一个班的学生在教室里通过浏览器访问，数据集中保存在教师主机上。

不涉及公网、不接学校统一认证、不做手机端。

## 2. 试点目标

### 2.1 业务目标

- 一个班（不超过 40 人）在同一局域网内同时使用，互不串数据。
- 学生刷新页面、关掉浏览器再打开，能回到原来的会话继续做。
- 教师在一台主机上收齐全班记录，不需要逐台电脑拷文件。
- 课堂上 AI 功能可用，但被限流，不会因为全班同时点而卡死。

### 2.2 技术目标

| 目标 | 指标 |
|---|---|
| 会话隔离 | 30 人并发时，任意两人看不到对方数据；无串号 |
| 会话恢复 | 刷新/重开浏览器后恢复成功率 100% |
| 页面响应 | 非 AI 操作 p95 < 1 秒（局域网） |
| AI 响应 | 5 个并发 AI 请求下，p95 首次回复 < 30 秒；报告草稿 < 90 秒 |
| 稳定性 | 连续运行 4 小时（两节课）不重启，内存无持续增长 |
| 数据完整 | 每个学生一个目录，写入不互相覆盖 |
| 鉴权 | 无课程码无法进入；伪造学号不能覆盖他人记录 |

### 2.3 非目标（本期不做）

- 公网访问、域名、HTTPS 证书
- 学校统一身份认证（CAS/OAuth/LDAP）
- 手机端适配（当前也不在项目范围内）
- 多班级排课、成绩管理、教师批改后台
- 多台服务器/多 worker 横向扩展
- 自动批改、防作弊

## 3. 现状与差距

### 3.1 现有能力

- Gradio 6.31 + Python 3.12，单进程。
- 完整教学流程：阶段0～4、双模式、AI 检查/批改/报告、CSV/Word 导出。
- 记录按学号写入 `records/<学号>/session_*.json`。
- `blocked_paths` 已禁止直接下载 `records/`。

### 3.2 阻碍多用户的点

| # | 问题 | 影响 |
|---|---|---|
| 1 | 全局 `session` | 第二个学生无法开始，或直接串到别人的会话 |
| 2 | 全局 `params`、`DOCK` | 参数与浮窗状态互相覆盖 |
| 3 | 回调全部读写全局 | 没有"当前用户"概念 |
| 4 | `queue(max_size=1, concurrency_limit=1)` + `concurrency_id="single_user"` | 所有请求串行 |
| 5 | 无认证 | 学号可伪造，课程码缺失 |
| 6 | `server_name="127.0.0.1"` | 局域网不可达 |
| 7 | 会话只在内存 | 刷新/重启即丢失 |
| 8 | AI 同步阻塞（timeout 20s） | 高并发排队 |

### 3.3 差距结论

第 1～3 条是**必须先改**的架构问题；第 4～8 条是部署与体验问题，可以在试点前补齐。

## 5. 技术方案

### 5.1 会话模型

- 新增 `UserContext`：把 `session`、`params`、`dock` 从模块全局移进去。
- 浏览器侧持有 `session_token`（`gr.State` + 签名 cookie 或 `gr.BrowserState`）。
- 回调签名改为 `handle(ctx, action, ...)`，`get_view_state(ctx)`；禁止再访问模块级 `session`。
- 服务端 `SessionRegistry`：`token -> UserContext`，带 TTL 和最后活跃时间。
- 刷新恢复：token → 注册表；注册表丢失时从 `records/<学号>/` 最新 JSON 重建界面状态。
- 同一学号重复登录：默认踢掉旧会话或提示"已在另一窗口打开"。

### 5.2 并发与队列

- 去掉 `single_user` 这个 `concurrency_id`。
- 三类事件分开：
  - 轻量读写（切阶段、保存表单）：高并发；
  - 文件/记录写入：按学生串行；
  - AI 调用：单独线程池（例如 4～6 个 worker），超时 30 秒，失败可重试一次。
- `queue(default_concurrency_limit=8)` 左右，按压测调整。
- 每个学生每分钟 AI 请求上限（建议 6 次），报告草稿每天上限（建议 3 次）。

### 5.3 认证与名单

- 进入页增加「课程码」输入，服务端校验（环境变量或配置文件）。
- 学号与教师提供的名单 CSV 比对；不在名单内拒绝。
- 可选：每个学生一个 4 位 PIN，防止互填学号。
- 教师机保留一份名单文件，支持热更新。
- 认证只做"能进门 + 认领学号"，不做复杂权限。

### 5.4 数据与存储

- 目录保持 `records/<学号>/session_*.json`，增加 `records/<学号>/index.json` 便于恢复。
- 写入继续用临时文件 + 原子替换；同一学生的写入加进程内锁。
- 报告和 CSV 继续放临时目录，下载后由系统清理。
- 每日 23:00 备份 `records/` 到另一块盘或共享目录，保留 14 天。
- 提供教师用的只读汇总脚本（按学号导出 CSV/Word 清单），本期可不做界面。

### 5.5 部署与网络

- 主机：4 核 / 8 GB / SSD，Windows 11 或 Ubuntu 24.04。
- 有线接入教室局域网，固定 IP 或 DHCP 保留；建议配一个主机名，如 `torsion-lab`。
- 应用绑定 `0.0.0.0:7862`；Windows 防火墙只放行入站 7862，并限制在本地子网（教室网卡常被识别为「公用」，不要只写 `profile=private`）。
- 开机自启：Windows 用任务计划或 NSSM；Linux 用 systemd。
- 关闭睡眠/休眠；关闭自动重启更新（或设定维护窗口）。
- 本期不上 HTTPS：仅限受控局域网，明确告知学生不要在校外访问。

### 5.6 安全边界

- 仅在教室局域网开放，不映射公网端口。
- API key 只放服务端环境变量，不进仓库、不进前端。
- `blocked_paths` 保留；报告下载接口只允许本人会话。
- 日志不记录完整 AI 对话内容，只记时间、学号、耗时、结果状态。
- 试点前告知学生：数据保存在教师主机、AI 提问会发送给模型服务商。

## 6. 实施计划

### 阶段 P0：设计与基线（2 天）

- 确认试点班级、人数、设备、网络。
- 冻结一版单机代码作为回滚点（打 tag）。
- 输出接口清单：哪些回调要改成 `ctx`。

**退出标准**：改造清单确认，回滚 tag 就绪。

### 阶段 P1：多会话重构（4～5 天）

- 引入 `UserContext` 与 `SessionRegistry`。
- 迁移所有全局状态；回调改签名。
- 会话恢复（token + JSON 重建）。
- 同一学号重复登录处理。

**退出标准**：本机开 3 个浏览器，各自独立完成阶段1，互不影响；刷新可恢复。

### 阶段 P2：认证与名单（2 天）

- 课程码、名单校验、拒绝提示。
- 教师名单文件格式与更新方式。
- 登录失败限速（防爆破）。

**退出标准**：错误课程码/不在名单被拒；正确信息可进入。

### 阶段 P3：AI 异步与限流（2～3 天）

- AI 调用移入线程池，前端显示处理中。
- 每学生限流与每日配额。
- 超时与失败提示。

**退出标准**：5 个并发 AI 请求不互相阻塞；单学生超限被拒绝并提示。

### 阶段 P4：局域网部署（1～2 天）

- 主机环境、固定 IP、防火墙、自启。
- 启动脚本与健康检查。
- 备份任务。

**退出标准**：教室内 3 台不同机器可访问并完成一次完整流程。

### 阶段 P5：测试与试点（3 天）

- 功能回归（现有 `smoke_check.py` 全过）。
- 10 人、20 人、30 人渐进压测。
- 第一次课试点，第二次课修正后复测。
- 收集反馈，输出报告。

**退出标准**：第 2.2 节指标全部达标，或明确记录未达标项与原因。

### 总工期

约 **3 周**（不含教师排课与场地协调）。如果只做 P1 + P4 的最小版本，约 1 周，但缺少认证和限流，只适合完全信任的课堂环境。

| 风险 | 概率 | 影响 | 应对 |

- 不要 `git push --force`。
- 不要在 `main` 上直接提交试点代码。
- 不要删除、覆盖或移动现有 `records/`。
- 不要把课程码、API key、学生名单提交进仓库或写进日志。
- 不要修改单机版的端口、启动方式和页面行为。
- 不要把试点分支的产物当作正式分发版本。
